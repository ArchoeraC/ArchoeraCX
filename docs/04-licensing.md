# 04 · 许可证与合规

> **2026-10 更新：已定为 GNU Affero General Public License v3.0 only（AGPL-3.0-only），且不接受外部代码贡献。**
> 许可证全文见仓库根目录 `LICENSE`（官方 34,523 字节文本）；贡献政策见 `CONTRIBUTING.md`。
> 发行与下载策略见 `09-distribution-and-download-policy.md`。

> 这份文档的目标不是"选一个协议"，而是**先决定你要保护什么，再倒推协议**。

---

## 1. 核心结论

| 你的真实意图 | 应该选 | 代价 |
|---|---|---|
| **开源 + 最强 copyleft（当前选择）** | **AGPL-3.0-only** | 整作品 copyleft + 网络条款；App Store 不可用；企业/插件生态远离 |
| 开源 + 文件级 copyleft | MPL-2.0 | 只公开改过的文件；允许闭源 Larger Work |
| 开源、公共领域 | The Unlicense | 无署名要求；无商标/专利授权；任何人都能闭源再分发 |
| 闭源、免费 | 专有 EULA（All Rights Reserved） | 不能用任何 GPL/AGPL 代码；仍需履行 MIT/Apache 声明义务 |
| 保留闭源 / 商业授权 / 上架 App Store 的可能 | Apache-2.0 + CLA（可选） | 不能用 HMCL/Prism/Modrinth 的代码，只能参考 |
| 只想防竞品抄袭，接受"非开源" | BSL-1.1（带 change date） | 不是 OSI 开源；社区通常不买账；不能叫 open source |
| 纯个人项目，不在意被抄 | MIT | 无任何保护 |

**已定路径**：

```
现在：AGPL-3.0-only
  ├─ 代码：开源；分发/网络服务需提供完整对应源码
  ├─ 贡献：不接受外部代码贡献（版权 100% 自有）
  ├─ CLA：暂不需要；将来开放 PR 时再上
  ├─ 不能并入：第三方 GPL/AGPL 会保留其许可，未来闭源需替换
  └─ 商标：不在许可证内，需单独政策
```

> **关键洞察**：AGPL 是"最强的主流打手"，但它保护的是**代码自由**，不是"功能必须保留"。
> fork 仍可删掉下载门控；**你未来能闭源，是因为你拥有版权，不是因为 AGPL 允许你收回。**

## 2. 决策树

> 当前已定为 AGPL-3.0-only；本树保留用于复核与未来变更。

```
Q1. 未来 12–24 个月，是否可能需要闭源 / 卖商业授权 / 上 Mac App Store？
├─ 是
│   Q2. 是否愿意放弃复用任何 GPL/AGPL 代码（HMCL、Prism、Modrinth、SJMCL…）？
│   ├─ 是 → ★ Apache-2.0（+ CLA）           【推荐】
│   └─ 否 → 只能永久开源，见 Q3
└─ 否
    Q3. 是否希望"网络服务端也必须开源"（AGPL 的网络条款）？
    ├─ 是 → AGPL-3.0-only
    └─ 否 → GPL-3.0-only 或 MPL-2.0
```

补充判断：

> 注：如果你只是"保留未来关源的能力"，而不打算做商业闭源/上架 App Store，AGPL + 100% 自有版权（不收外部贡献）同样可行——见 §4「保留关源能力」。本树是通用决策工具，不是对当前选择的否定。

- **要上 Mac App Store** → 排除 GPL/AGPL（Apple 的 DRM 与附加限制条款与之冲突，历史上有 VLC 下架先例）。
- **要做云同步/账户后端** → 若后端也 AGPL，则网络用户有权获取后端源码；若不想，后端必须独立且不构成"单一程序"。
- **要做插件生态** → 核心用 MIT/Apache，插件接口用宽松协议；AGPL 会吓退所有第三方插件开发者。

## 3. 许可证对比

| 协议 | 闭源分发 | 修改后必须开源 | 网络条款 | 可与 GPL 代码合并 | 上架 App Store | 社区接受度 |

| MIT | ✅ | ❌ | ❌ | ✅（GPL 项目可用 MIT 部分） | ✅ | 最高 |
| Apache-2.0 | ✅ | ❌ | ❌ | ✅（进 GPLv3） | ✅ | 高（含专利授权） |
| MPL-2.0 | ✅（文件级） | ✅（仅改过的 MPL 文件） | ❌ | ✅（§3.3 可转为 GPL/AGPL） | ✅ | 中 |
| LGPL-3.0 | ✅（动态链接/独立进程） | ✅（库本身） | ❌ | ✅ | ⚠️ | 中 |

| 自定义/闭源 | ✅ | — | — | ❌ | ✅ | — |

## 4. 方案库

### 方案 M · MPL-2.0（备选）

**定义**：文件级 copyleft。修改过的 MPL 文件必须以 MPL 提供源码；与其它代码组成的"Larger Work"可以用其它条款分发。

| 维度 | 结论 |
|---|---|
| OSI / SPDX | 是；`MPL-2.0` |
| 必须开源的部分 | **修改过的 MPL 文件**（不是整个项目） |
| 新增文件 / 插件 / 外壳 | 可以闭源（Larger Work） |
| 专利 | **明确授权**（含专利诉讼终止条款） |
| 商标 | **不授权**；名称/Logo 需另立政策 |
| 闭源 fork | 允许（但 MPL 文件仍须 MPL） |
| 撤回 | 已发布版本的授权不可撤回 |
| 与 MIT/Apache/BSD 合并 | 允许，保留原声明 |
| 与 GPL/AGPL 合并 | ⚠️ MPL 部分可作为 Secondary License 分发；但并入 GPL 代码会让整包受 GPL 约束 |
| App Store | ✅ 通常可行 |

**它带来的三个现实问题**：

1. **门控仍不可强制**：fork 可以删掉下载限制；它只需把改过的 MPL 文件公开。
2. **"文件级"容易被误解**：不是"整个项目必须开源"，也不是"可以随便闭源改核心"。
3. **商标不在许可证里**：官方构建、名称、Logo 仍需单独保护。

**我们的应对**：
- 每个源文件加 Exhibit A 头（或至少在 LICENSE 说明）；
- 修改过的核心文件保持 MPL，新增插件/外壳可闭源；
- 官方构建签名 + 校验和 + 官方下载页；
- 名称/Logo 商标政策，fork 必须改名；
- 下载策略做成"构建期通道 + 运行期默认值"，不宣称强制；
- 发行与下载细节见 `09-distribution-and-download-policy.md`。

> 如果将来想"更强 copyleft"（防闭源商用/云厂商），再评估 AGPL；但 AGPL 与 App Store 冲突。
> 如果只想"最大自由"，才选 Unlicense/0BSD。

### 方案 U · The Unlicense（备选）

**定义**：放弃版权，将软件投入公共领域（在承认版权的法域）；不承认的法域回退到无限制许可。

| 维度 | 结论 |
|---|---|
| OSI / SPDX | 是；`Unlicense` |
| 署名 | 不要求（可以删掉你的名字） |
| 商标 | **不授权**；名称/Logo 需另立政策 |
| 专利 | **无明确授权**（弱于 Apache-2.0） |
| 闭源 fork | 允许 |
| 撤回 | **不可能**（已发布版本永久公共领域） |
| 与 MIT/Apache/BSD 合并 | 允许，但那些文件仍受原许可约束（保留声明/NOTICE） |
| 与 GPL/AGPL 合并 | **不可以**；会让分发受 GPL/AGPL 约束 |

**它带来的三个现实问题**：

1. **门控不可强制**：任何人 fork 后都能删掉下载限制；代码里的开关只是默认值。
2. **无法阻止换皮/加广告**：只能靠商标、签名、官方渠道区分"官方构建"。
3. **无专利授权**：如果将来引入专利算法/编解码器，风险自担。

> 若你更在意"防止闭源换皮"，MPL-2.0 是更合适的选择；Unlicense 是"最大自由"，不是"最大保护"。

### 其它备选（如果不用 AGPL）

| 许可证 | 类型 | 闭源 fork | 必须开源的部分 | 专利授权 | 署名 | App Store | 适合 |
|---|---|---|---|---|---|---|---|
| **MPL-2.0** | 文件级 copyleft | ✅（新增文件可闭源） | 修改过的 MPL 文件 | ✅ | ✅ | ✅ | 备选：防"改核心闭源"，允许闭源插件/外壳 |
| **Apache-2.0** | 宽松 | ✅ | 无 | ✅ | ✅ + NOTICE | ✅ | 要采用率 + 专利保护 |
| MIT | 宽松 | ✅ | 无 | ❌ | ✅ | ✅ | 最简单、最通用 |
| BSD-3-Clause | 宽松 | ✅ | 无 | ❌ | ✅ | ✅ | 类似 MIT + 禁止背书 |
| ISC | 宽松 | ✅ | 无 | ❌ | ✅ | ✅ | 更短 |
| **0BSD** | 公共领域等价 | ✅ | 无 | ❌ | ❌ | ✅ | 想无署名，但比 Unlicense 更像"许可证" |
| CC0-1.0 | 公共领域 | ✅ | 无 | ❌ | ❌ | ✅ | 更适合素材/文档；软件有争议 |
| LGPL-3.0 | 弱 copyleft（库） | 动态链接可 | 库本身 | ✅ | ✅ | ⚠️ | 库/插件，不适合应用本体 |
| GPL-3.0 | 强 copyleft | ❌ | 整个作品 | ✅ | ✅ | ❌ | 永久开源 |
| AGPL-3.0 | 强 + 网络条款 | ❌ | 整个作品 + 网络服务 | ✅ | ✅ | ❌ | 防云厂商/闭源商用 |
| EPL-2.0 | 弱 copyleft | ✅（模块） | 修改的 EPL 文件 | ✅ | ✅ | ✅ | 与 GPL 不兼容，不推荐 |
| BSL-1.1 | 源码可见 | ✅（非竞争） | 无（源码可见） | ❌ | 视配置 | ✅ | 防竞品，但**不是 OSI 开源** |
| Elastic-2.0 | 源码可见 | 禁止提供竞品服务 | 无 | ❌ | ✅ | ✅ | 防 SaaS 复制 |
| PolyForm Noncommercial | 源码可见 | 仅非商业 | 无 | ❌ | ✅ | ✅ | 非商业项目 |
| SSPL | 源码可见 | 禁止 | 服务端 | ❌ | ✅ | ✅ | 非 OSI，尽量避免 |

**选择建议**

| 你的优先级 | 选它 | 理由 |
|---|---|---|
| 防止闭源换皮，同时保留插件生态 | **MPL-2.0** | 只要求"改过的 MPL 文件"公开；新增文件可闭源；可转 GPL/AGPL |
| 最大采用率 + 专利保护 | **Apache-2.0** | 专利授权 + NOTICE；企业最熟悉 |
| 极简、只要署名 | MIT / BSD-3 / ISC | 生态兼容性最好 |
| 公共领域、不要署名 | **0BSD**（优于 Unlicense） | 真正的许可证文本，不依赖"放弃版权"在各地域的效力 |
| 永久开源、防闭源商用 | **AGPL-3.0** | 网络条款覆盖服务端；但 App Store 不可用 |
| 想卖商业授权 | **AGPL + CLA** 或 **open core** | 需要从第一天收 CLA，否则无法双许可 |
| 只防竞品、可接受非开源 | BSL-1.1 | 有 change date，几年后转 Apache |

**三个必须知道的点**

1. **没有任何开源许可证能阻止 fork 删除下载门控**。GPL/AGPL 只要求它公开源码，不要求它保留功能；MPL 只要求它公开改过的文件。
2. **Unlicense / 0BSD / CC0 都没有专利授权**；Apache-2.0 和 MPL-2.0 有。
3. **商标永远不在许可证里**。无论选哪个，名称/Logo 都要单独做政策。

> 如果你希望"别人改了核心必须开源，但插件可以闭源"，MPL-2.0 是这类项目最合适的选择；如果只是想让更多人用，Apache-2.0 更稳。

### 强 copyleft 备选（"打手"型）

如果你要的是"像 AGPL 一样管得宽"，先看这张表。**AGPL 仍是事实标准**，其它选项各有硬伤。

| 许可证 | 网络/SaaS 条款 | OSI | 与 GPL 兼容 | 专利授权 | App Store | 采用度 | 一句话 |
|---|---|---|---|---|---|---|---|
| **AGPL-3.0** | ✅ §13（网络交互即触发） | ✅ | ✅（与 GPLv3 互相） | ✅ | ❌ | **高** | **当前选择**；最强的主流选择 |
| **EUPL-1.2** | ✅（communication to the public / SaaS） | ✅ | ✅（兼容条款可转 GPL/AGPL/MPL…） | ✅ | ⚠️ | 中（欧洲公共部门） | "欧洲版 AGPL"，但兼容条款可能稀释 |
| **OSL-3.0** | ✅ §5 External Deployment | ✅ | ❌ | ✅ | ❌ | 低 | 最接近 AGPL，但冷门、未上过庭 |
| **RPL-1.5** | ✅ Deployment | ✅ | ❌ | ⚠️ | ❌ | 很低 | 更冷门，生态几乎为零 |
| **CPAL-1.0** | ✅（网络归属） | ✅ | ❌ | ⚠️ | ⚠️ | 低 | 归属条款麻烦，不建议 |
| **SSPL-1.0** | ✅（服务整体源码） | ❌ | ❌ | ❌ | ❌ | 中（MongoDB） | 最强，但**不是开源** |
| **GPL-3.0** | ❌（只有分发触发） | ✅ | ✅ | ✅ | ❌ | 高 | 强 copyleft，但管不到 SaaS |

**怎么选**

| 目标 | 选择 | 代价 |
|---|---|---|
| 最强、最被认可的"开源打手" | **AGPL-3.0-only** | 企业避开、插件生态难、App Store 不行 |
| 要 AGPL 的网络条款 + 欧洲法/多语言/兼容性 | **EUPL-1.2** | 兼容条款允许转成更弱的许可，保护可能被"降级" |
| 想用 AGPL 但不愿背 AGPL 的名声 | **OSL-3.0** | GPL 不兼容、案例极少、社区认知低 |
| 连 SaaS 的编排/管理代码都要开源 | **SSPL-1.0** | 不是 OSI 开源，别对外称 open source |
| 应用要最强，插件生态要活 | **AGPL 应用 + MPL/Apache SDK** | 维护两套许可边界 |
| 想保留商业闭源版 | **AGPL + CLA** | 必须从第一天收 CLA |

**三个现实提醒**

1. **AGPL 的"全能"只在版权范围内**：它不管商标、不管数据、不管服务条款；这些要单独做。
2. **AGPL 的执行成本高**：你得拥有版权（或 CLA）才能维权；社区贡献没有 CLA 时，你只能以 AGPL 维权，不能双许可。
3. **越强的 copyleft，越少人用**：如果目标是"被广泛采用 + 防止闭源换皮"，MPL 往往比 AGPL 更有效——因为 AGPL 直接把商业用户吓跑。

> 对你这个项目，**AGPL 是"打手"，MPL 是"防线"**：AGPL 逼所有人开源，MPL 只逼改核心的人开源。想两者都要，就用 **AGPL 应用 + MPL SDK** 的混合。

### 方案 0 · 闭源免费（历史方案）

**定义**：源码不公开，二进制免费分发；用户获得"使用许可"，不获得复制/修改/再分发源码的权利。

**主许可证**：自拟 EULA（或基于成熟模板改写），核心条款：

| 条款 | 建议 |
|---|---|
| 授予 | 免费、非独占、可撤销的使用许可（个人/商业使用均可，按你的意愿） |
| 限制 | 不得反向工程/反编译（注意：部分司法辖区允许互操作性目的的反向工程，条款不能完全排除） |
| 分发 | 允许原样转发安装包，禁止修改后分发、禁止捆绑 |
| 无担保 | "AS IS"，不承担数据丢失/封号等责任 |
| 终止 | 违反条款即终止 |
| 隐私 | 单独一份隐私政策（若收集任何日志/设备信息） |

**依赖白名单**（可进闭源构建）：

```
MIT · BSD-2/3 · Apache-2.0 · ISC · Zlib · Unlicense · CC0 · OFL(字体) · 公共领域(SQLite)
```

**禁止进入构建**：

```
GPL-2/3 · AGPL-3 · SSPL · BUSL · Commons Clause · CC-BY-NC(代码) · 任何"仅非商业"许可
```

**LGPL**：动态链接/独立进程在满足条件时可行（可替换库、提供库源码、声明），但在你的多语言静态打包场景里容易踩坑，**建议直接避开**。

**必须履行的义务**（闭源也必须做）：

1. MIT/BSD/ISC：在"关于 → 第三方许可"中保留版权声明与许可全文。
2. Apache-2.0：额外保留 `NOTICE` 文件，标注修改过的文件。
3. OFL 字体：保留字体名称与许可，不单独售卖字体。
4. 分发 `authlib-injector`（AGPL-3.0）：提供其源码获取方式（链接官方仓库即可），并单独声明。
5. 不得移除他人版权头。

**不需要做的事**：

- 不需要公开自己的源码；
- 不需要提供构建脚本；
- 不需要 CLA（除非接受外部贡献；建议初期不接受）。

**容易忽略的三件事**：

1. **免费 ≠ 无隐私义务**：只要收集设备信息/崩溃日志，就要有隐私政策与 opt-in（尤其面向欧盟/中国用户）。
2. **闭源 ≠ 安全**：NativeAOT/混淆只提高逆向成本。**永远不要把 client secret、私钥放进客户端**；OAuth 用公共客户端 + device code。
3. **保留版权才能以后开源**：不接受无 CLA 的外部贡献，未来你仍可单方面选择 Apache/AGPL 发布。

**与商标的关系**：许可证管代码，商标管名字。即使闭源，也不能用 "Minecraft" 作为产品名主体，必须附免责声明。

### 方案 A · AGPL-3.0-only（当前选择）

**适用**：明确不做商业闭源、希望"任何人分发/提供网络服务都必须开源"，且不接受外部贡献以保持版权集中。

- 许可证：`AGPL-3.0-only`（不要用 `-or-later`，除非你接受未来 FSF 改版）。
- 贡献：**当前不接受外部代码贡献**（见 `CONTRIBUTING.md`）；将来开放 PR 时需 CLA，否则无法把含他人贡献的版本闭源。
- GPL 兼容：技术上可按 GPLv3 §13 并入 GPL-3.0 代码，但**这些文件仍是 GPL-3.0**；如果保留"未来闭源"选项，**不要并入**。本项目不采用。
- 义务：分发二进制时提供完整对应源码；若提供网络服务（同步、账户、遥测后端），网络用户可获取该服务源码。
- 风险：Mac App Store 不可用；部分企业用户直接排除；第三方插件生态基本不会形成；不收贡献意味着维护压力集中在作者身上。

**注意**：即使选了 AGPL，也**不建议**直接粘贴 HMCL/Prism 代码——架构差异大，且会破坏未来的闭源选项。

### 方案 B · 保留所有选项（Apache-2.0，备选）

**适用**：产品形态未定，可能商业化，也可能以后开源。

- 许可证：`Apache-2.0`，附 `NOTICE`。
- 贡献：DCO（轻量）；若认真考虑"未来闭源/双许可"，则必须 **CLA**（否则你无权重新许可他人的贡献）。
- 代码来源：只允许 MIT / Apache-2.0 / BSD / ISC；GPL 项目**只读**。
- 未来：
  - 转 AGPL：可以（自己的代码随便改；Apache-2.0 贡献可被包含进 AGPL 作品）。
  - 转闭源：只有签过 CLA 的贡献才行；没有 CLA 的部分必须保持 Apache-2.0（可作为独立组件继续开源）。
- 代价：放弃了"直接抄成熟实现"的捷径。

### 方案 C · 文件级保护（MPL-2.0）

**适用**：希望核心文件保持开放、但允许闭源外壳/插件/商业发行。

- 修改过的 MPL 文件必须以 MPL 公开；新增文件可闭源。
- 可被并入 GPL/AGPL 项目（§3.3），因此未来转 AGPL 也顺。
- 不适合"防止别人拿去做竞品"——别人可以闭源新增大量代码。

### 方案 D · 源码可见（BSL-1.1）

**适用**：只想阻止竞争者直接拿去卖，愿意牺牲"开源"名分。

- 参数：Additional Use Grant（允许个人/非商业）、Change Date（如 4 年后转 Apache-2.0）、Change License。
- 典型：GDLauncher Carbon。
- 代价：不能自称 open source；Linux 发行版/Flatpak 通常拒绝；社区贡献意愿低。

### 保留"以后关源"的能力（重要）

先说结论：**开源许可不可撤回。**
你能做的是"停止发布新版本"或"未来版本闭源"，不能把已经发布的 AGPL 代码收回。

| 动作 | 可行 | 条件 / 说明 |
|---|---|---|
| 把仓库设为私有 | ✅ | 随时；但已获得代码的人仍可继续按 AGPL 使用、fork |
| 停止发布新版本 | ✅ | 随时 |
| 让已发布的 AGPL 版本"失效" | ❌ | 开源许可对已发布版本持续有效 |
| 未来版本改为 proprietary | ✅ | **你拥有该版本的全部版权**（不接受外部贡献，或已收 CLA） |
| 闭源分发但仍含 AGPL 代码 | ⚠️ | 必须向接收者提供完整对应源码；做不到就要重写/替换 |
| 阻止别人 fork 代码 | ❌ | 许可证管不了；只能靠商标限制名字 |

**必要条件：版权集中**

- **不接受外部贡献**（当前选择，最简单）；或
- **CLA**：贡献者授予你"可重新许可"的权利（或版权转让）。**DCO 不够**。
- CLA 只覆盖**未来**版本；已发布版本仍是 AGPL。

**三种可落地模式**

| 模式 | 做法 | 代价 |
|---|---|---|
| **Open → Close**（AGPL + 不收贡献） | 现在 AGPL 开源；将来由版权人把新版闭源 | 不能收外部 PR；否则需要 CLA |
| **Open Core** | 核心 AGPL；商业模块 proprietary | AGPL 的"整个作品"边界很宽，链接式闭源模块风险高；要用独立进程/明确边界 |
| **Source-available**（BSL） | 源码可见、限制竞争，几年后转 Apache | **不是开源**，别自称 open source |

**AGPL 下"闭源版"的具体义务**

1. 你**自己的代码**：作为版权人，可以把未来版本换成 proprietary；
2. **第三方 AGPL/GPL 代码**：仍受原许可约束，闭源版里必须替换或遵守（提供源码）；
3. **已分发的旧版本**：接收者的 AGPL 权利不受影响；
4. 若通过网络提供服务，AGPL §13 仍可能要求向用户提供源码——闭源版不要复用这部分服务端代码，除非你拥有它。

**操作清单**

- [x] 不接受外部代码贡献（见 `CONTRIBUTING.md`）
- [ ] 记录每个文件的来源与作者（git 历史 + SBOM）
- [ ] 关源前做版权审计：哪些文件是自有、哪些是第三方 AGPL/GPL
- [ ] 闭源版剔除/替换第三方 copyleft 代码
- [ ] 关源后保留旧版本源码归档（对已分发用户）
- [ ] 商标/名称政策，防止 fork 冒充官方

> 一句话：**"开源 + 随时能收回"不存在；"开源 + 未来版本可闭源"存在，前提是版权没有分散。**

---

### 不推荐

- **GPL-3.0（而非 AGPL）**：对桌面启动器而言，AGPL 的额外约束只在"网络服务"场景生效；如果你不打算做服务端，两者差别不大。但 GPL 已足够阻止闭源，且兼容性更广。若倾向 copyleft，优先 AGPL 或 MPL，理由更清晰。
- **"先 AGPL，以后再闭源"**：法律上只能对**未来版本**成立，且必须 CLA + 完全自有代码；已发布版本收不回来。

## 5. 代码组合规则（速查）

| 你的代码 | 引入的第三方代码 | 结果 |
|---|---|---|
| 闭源 | MIT / BSD / Apache-2.0 | ✅ 可，保留声明与 NOTICE |
| 闭源 | MPL-2.0 | ✅ 可，改过的 MPL 文件需公开 |
| 闭源 | LGPL-3.0（动态链接/独立进程） | ⚠️ 可，需可替换、提供库源码与声明 |
| 闭源 | GPL-3.0 / AGPL-3.0 | ❌ 不可 |
| AGPL-3.0 | MIT / Apache-2.0 / MPL-2.0 | ✅ 可 |
| AGPL-3.0 | GPL-3.0 | ✅ 可（GPLv3 §13），该部分仍为 GPL |
| AGPL-3.0 | BSL / 自定义 | ❌ 不可 |
| GPL-3.0 | AGPL-3.0 | ⚠️ 可合并（GPLv3 §13）；GPL 部分仍是 GPL，需同时满足两套义务 |
| 任意 | 无 LICENSE 的仓库 | ❌ 默认保留所有权利，等同闭源 |

**独立进程 ≠ 一定隔离**：把 GPL 程序作为独立可执行文件调用（例如自行调用的转换 CLI）通常属于"聚合"，不传染；但如果通过紧密的私有协议交换数据结构、共享地址空间，则可能被认定为单一作品。**边界要留清楚：命令行调用 + 标准文件/HTTP 交互。**

## 7. 工程化合规

### 7.1 仓库基线

```
LICENSE                 # AGPL-3.0 全文（仓库根目录，34,523 字节）
NOTICE                  # Apache-2.0 依赖必需
THIRD-PARTY-NOTICES.md  # 自动生成，安装包内展示
PRIVACY.md              # 收集任何数据就需要
TRADEMARKS.md           # 名称/Logo 使用政策（AGPL 不授权商标）
CONTRIBUTING.md         # 明确「不接受外部代码贡献」；开放时需 CLA
```

**每个源文件建议加 SPDX 头**：

```
// SPDX-License-Identifier: AGPL-3.0-only
// Copyright (C) 2026 <作者/项目名>
```

AGPL 的应用条款建议（按官方模板）：

```
This program is free software: you can redistribute it and/or modify
it under the terms of the GNU Affero General Public License as published by
the Free Software Foundation, version 3 of the License.
```

> 若将来接受外部贡献，必须同时具备：CLA（重许可权）+ 来源审计 + 文件头。否则"未来闭源"只能覆盖你自有的部分。

### 7.2 CI 检查

| 检查 | 工具 |
|---|---|
| 依赖许可证白名单 | `dotnet list package --include-transitive` + `nuget-license`；Flutter 用 `flutter pub deps` + `license_checker` |
| 源码头 SPDX | `reuse`（FSFE）或自定义脚本 |
| SBOM | `dotnet CycloneDX` / `syft` |
| 禁止 GPL 进入构建 | 构建脚本里显式断言（白名单之外直接 fail） |
| 资产来源 | `assets/icons/loaders/SOURCES.md`、`assets/icons/ui/SOURCES.md` 记录每个图标/字体的来源与许可，许可正文放 `assets/licenses/` |

### 7.3 发布物

- 安装包内提供"第三方许可"页面（读取 `THIRD-PARTY-NOTICES.md`）。
- 若 AGPL：下载页提供对应源码归档（含构建脚本），并注明获取方式。
- 若分发 `authlib-injector`：附其 AGPL 声明与源码链接。

### 7.4 CLA / DCO

| | DCO | CLA |
|---|---|---|
| 作用 | 声明有权提交该代码 | 把版权/再许可权授予项目方 |
| 能否支持未来闭源 | ❌ | ✅ |
| 贡献者接受度 | 高 | 低 |
| 建议 | 方案 A/B 初期 | 一旦认真考虑双许可，立刻启用 |

> 现实做法（AGPL + 不收贡献）：**不需要 CLA**，因为你拥有全部版权；但要在 `CONTRIBUTING.md` 明确"不接受外部代码贡献"。
> 将来若开放 PR，必须先上 CLA（重许可权），否则无法把包含他人贡献的版本闭源。

## 9. 常见误解

| 误解 | 事实 |
|---|---|
| "GitHub 公开就能随便用" | 公开 ≠ 授权；无 LICENSE 即保留所有权利 |
| "AGPL 只影响服务端" | 桌面程序分发同样触发源码义务；网络条款是**额外**的 |
| "改一改就不算抄" | 改写/翻译/换语言仍是衍生作品 |
| "只抄思路不算抄" | 思路一般不受版权保护，但**具体表达、结构编排、资产**受保护；不要照搬目录结构与命名体系 |
| "开源项目没有专利风险" | Apache-2.0 有明确专利授权；MIT 没有；GPLv3 有隐含专利条款 |
| "用了 MIT 库就可以不署名" | 必须保留版权与许可声明 |
| "先把代码抄进来，以后再说" | 一旦发布就构成侵权，且无法"洗白"历史 |
